2015 moed A, question 1 (30 points). Gear knows its center, radius, and left and right neighbors. move turns this gear and both neighbors, in the opposite direction. SimpleGear stores a _state angle.

a. Define an invariant. b. check validates constructor arguments against that invariant. c. Is the class safe under every interleaving? If not, show one. d. After _state is updated inside move, moveLeft, and moveRight, is it safe? Show a bad interleaving or argue. e. Preconditions and postconditions of move. f. A Spinner thread calls move on a gear. Is a run of several spinners correct if "correct" means the sequence of states is one that a serial order of move calls could produce? Repair it if not.

Hint 1 of 3

The geometric invariant is about radii and centers: meshing gears have to actually touch, and a gear is not its own neighbor.

Hint 2 of 3

_state = _state + delta is a read-modify-write on a field the neighbor's thread also writes, because move calls into the neighbor.

Hint 3 of 3

A serial order means each move finishes before the next starts. Two spinners on adjacent gears overlap.

Solution

Invariant: radius is positive; left and right, if set, are different gears; a neighbor's center is exactly radius + neighbor.radius away on the x axis; _state stays in [0, 360).

check rejects a non-positive radius and a center that would break the mesh when the neighbor is already set.

Without synchronization, two move calls on adjacent gears interleave their _state updates and the recursive calls into each other. One gear's angle can be applied twice or lost. That is a race, so the class is not safe.

Adding _state updates inside the three methods does not create safety. Thread A runs move on g1 and has entered g2.moveRight. Thread B runs move on g2 and writes _state between A's read and write. The same lost update remains.

Precondition of move: the invariant holds, and the neighbor chain reachable from this gear does not contain a cycle that this call would follow forever. Postcondition: this gear's angle has changed by its step, and each neighbor's angle has changed by the opposite step, and the invariant still holds.

Several Spinner threads do not produce a serial history, because their move calls overlap on shared gears. Make each public method synchronized on a single lock ordered along the chain, or lock a dedicated simulation lock around move, so each call finishes before the next begins. Per-gear locks deadlock if move locks this gear and then the neighbor while the neighbor locks itself and then this gear. The 2015 B solution's repair for that cycle is one ordered lock, or one semaphore for the whole mesh.

2015 moed A, question 2 (30 points). A vector stores elements in a contiguous array and can resize. The course decides that is wasteful, and asks for mvector<T>, whose memory is exactly the cells it needs, stored as a linked list.

a. (15) Implement the functions. You may add helpers. You may not add fields or change signatures. insertAt always succeeds, allocating if it must, and inserts at pos. removeAt shrinks the structure and, if pos is empty, returns some dummy T. Access to a linked-list cell is not O(1).

b. (5) Yosi suggests deleting the _len field and returning sizeof(_head) as the length. Choose the best description.

  1. It works and returns the length.
  2. Almost: divide by sizeof(T).
  3. On a 32-bit machine it always returns 4.
  4. It does not compile, because sizeof cannot be used with a template.
  5. None of the above.

c. (10) Draw the stack, the heap, and the vtable at the marked comment, for a by-value call foo(mvector<T> vec).

The official solution's class skeleton is a node<T> list with _len and _head, plus getSize, pushAt, and popAt.

Hint 1 of 3

sizeof is a compile-time size of a type, not a count of nodes reached by walking _next.

Hint 2 of 3

A parameter taken by value is a second object. Its pointer member and the caller's pointer member are two stack slots. Whether they share one list is exactly the copy constructor.

Hint 3 of 3

_head has pointer type. On the 32-bit machines this exam is thinking about, a pointer is 4 bytes.

Solution

a. The official solution stores a singly linked node<T> and a length. The destructor walks _len nodes and deletes each. copy allocates a fresh node per element and is used by the copy constructor. Assignment in that solution calls copy and returns *this (it does not first destroy the old list; a complete assignment also has to free the previous nodes, or it leaks). pushAt walks to pos, filling missing links with default nodes, then links a node that holds val. getSize returns _len.

b. The official solution marks 3. _head is a pointer. sizeof(_head) is the size of that pointer, which is 4 on a 32-bit machine, not the number of elements. Dividing by sizeof(T) is still a pointer size, not a length. The expression does compile inside a template.

c. At the line inside foo, the caller's mvector is one object and the parameter vec is another, because the parameter is passed by value. Each object occupies a stack slot (the _head pointer and _len). The nodes are on the heap. The official marking notes deduct for a missing return address, for drawing the parameter as if it were not passed by value, for putting the vector object itself on the heap, and for a vtable the class does not have. Shallow-copy drawings were accepted: both stack objects' _head pointers can aim at one node chain if the copy constructor was not a deep copy. A deep copy draws a second chain.

2015 moed A, question 3 (30 points). Keep the reactor, but talk to every client through one DatagramSocketChannel instead of a TCP SocketChannel per client. send and receive are non-blocking and return immediately. receive returns the sender's address, or null if nothing arrived.

a. (20) Say which methods you change. Do not rewrite methods you leave alone. b. Name one advantage and one disadvantage of UDP here. Can one DatagramSocketChannel replace the per-client channels? Does a channel per client help?

Hint 1 of 3

There is no connection to accept. The ConnectionAcceptor has nothing to do.

Hint 2 of 3

The reply must be sent to the address receive returned. Store that address with the outgoing buffer.

Hint 3 of 3

The official solution deletes the server socket channel and the acceptor, and registers the datagram channel for read and write.

Solution

a. As in the official solution: remove ServerSocketChannel and SocketChannel, create one non-blocking DatagramSocketChannel bound to the port, and register it for OP_READ | OP_WRITE. Delete ConnectionAcceptor. One ConnectionHandler calls non-blocking receive into a ByteBuffer and learns the SocketAddress. Protocol tasks must carry that address, and write sends through the datagram channel to the stored address. The output queue holds (address, buffer) pairs, not bare buffers.

b. UDP avoids the handshake and the per-client socket, and it can lose or reorder datagrams. One channel is what the design uses, because UDP has no connection to demultiplex with accept; the remote address is the demultiplexing key. A channel per client adds state the protocol does not need and does not make delivery reliable.

2015 moed B, question 1 (30 points). SimpleGear's public methods are all synchronized. Neighbors call each other's moveLeft / moveRight, which also need the neighbor's lock.

a. (7) Show a deadlock of several gears. b. (18) Remove it in three ways: narrowing the synchronization, and using a semaphore instead of synchronized, and one further way that keeps the program correct. c. (5) Which way do you adopt, and why?

Hint 1 of 3

Gear A locks itself and calls B, which locks itself and calls A.

Hint 2 of 3

A semaphore of one permit, taken in a fixed order, is a mutex that is not tied to the gear's this.

Hint 3 of 3

The official note prefers the repair that does not hold a lock the critical section does not need.

Solution

a. A.move locks A and calls B.moveRight, which tries to lock B. Concurrently B.move locks B and calls A.moveLeft, which tries to lock A. Each holds one monitor and waits for the other.

b. Three correct repairs. Narrow the synchronized regions so a gear does not call a neighbor while holding its own lock: copy the facts you need, unlock, then call. Use one Semaphore(1) for a whole connected mesh, acquired before any move and released after, so there is a single lock and no cycle. Take per-gear locks in address order, or in a left-to-right order, so every thread locks the earlier gear first. All three keep a single move atomic with respect to other moves.

c. The official solution says the narrowed synchronization is the one to adopt: the other two hold a resource the critical section does not need for the whole call. Order and the mesh semaphore are correct and coarser.

2015 moed B, question 2 (30 points). mvector is now an array of node, not a list. insertAt at a pos past the end grows the array to the smallest power of two strictly larger than pos (an empty vector, insert at 5, becomes length 8). removeAt shrinks by half once every element in the upper half has been removed (length 8, after the four high elements are gone, becomes 4). Elements keep their indexes. node has a pure virtual duplicate().

a. (15) Implement the underlined operations, including a deep copy constructor. Helpers are allowed. Do not add fields or change signatures.

b. (10) my_node derives from node and adds a long _data. Assume its functions are correct. Draw stack and heap for this run, up to the comment:

void foo(mvector vec) {
    mvector my_vec(vec);
    // ***** here *****
}
void main() {
    mvector vec;
    node* n = new my_node("test");
    vec.insertAt(*n, 3);
    foo(vec);
}

c. (5) Someone adds, at the end of main:

my_node* m = (my_node*)(vec.getAt(0));

Choose the best statement.

  1. Downcasting is forbidden in C++, so this is an error.
  2. A cast can never check compatibility at compile time.
  3. A downcast is safe only when the class has no virtual methods.
  4. Virtual methods are bound late, at run time.
  5. None of the above.

Hint 1 of 3

Growth is "smallest power of two that can hold index pos", and the old cells are copied by value into the new array before the old array is deleted.

Hint 2 of 3

foo takes mvector by value, then copy-constructs my_vec from that parameter. Count three vector objects, not one.

Hint 3 of 3

getAt returns a node*. The added line is a C-style cast. The official choices are about what is true of virtual functions, not about whether the cast is pretty.

Solution

a. The official copy constructor allocates a new array of _len and assigns each cell from the source. insertAt, when pos >= _len, sets the new length to the next power of two above pos, allocates, copies the old cells, deletes the old array, then writes the new element at pos and marks it not free. removeAt clears the cell and, when the high half is all free, allocates an array of half the length, copies, and deletes the old one. Because node is polymorphic, a truly deep copy of a my_node cell has to go through duplicate() rather than slicing the cell into a plain node. The published copy loop assigns cells; that is the official skeleton, and it will slice if node assignment does not call duplicate.

b. n points at a heap my_node. vec lives in main's frame; its array is on the heap, grown to 8, with the copy of the node at index 3. The call foo(vec) copy-constructs the parameter vec in foo's frame (a second array on the heap if the copy is deep). my_vec(vec) is a third vector in foo's frame and a third array. The vtable pointer sits in each my_node, because duplicate is virtual.

c. The official solution marks 4. Virtual methods are resolved at run time. Statement 1 is false: C++ allows a downcast. Statement 3 has the safety condition backwards: a checked dynamic_cast needs at least one virtual method. The line as written is a C-style cast, which does not perform that check.

2016 moed A, question 1 (30 points). Queue<T> has add(T item) and remove().

a. (8) Define an invariant for the interface, and pre- and postconditions for the methods. Add methods to the interface if you need them to state the contract.

b. (6) Complete testAdd and testRemove in TestQueue. createQueue() returns the object under test. setUp builds a fresh queue.

c. The question then shows the dining philosophers with a hand-rolled Semaphore and asks about deadlock, livelock, and starvation. That part is concurrency. Here, answer the contract.

Hint 1 of 3

remove on an empty queue has no honest postcondition unless you forbid the call.

Hint 2 of 3

You need a query, size or isEmpty, or the invariant cannot be stated.

Hint 3 of 3

A test that only calls add and never looks at the queue does not check a postcondition.

Solution

Add int size() and boolean isEmpty().

Invariant: size() >= 0, and isEmpty() if and only if size() == 0. The elements are in insertion order: the next remove yields the earliest add that has not been removed.

add(item): precondition item meets whatever the queue promises about null (if null is forbidden, say so). Postcondition: size() is one greater, and a later sequence of remove still yields the old elements, followed by item.

remove(): precondition !isEmpty(). Postcondition: size() is one smaller, and the removed element was the oldest.

testAdd records nothing, pushes one element, and checks size() == 1 and that the element is the one that remove returns. testRemove on an empty queue expects the precondition failure. testRemove after one add checks that size returns to 0 and the value matches. setUp must give each test a new queue so leftovers do not look like invariant failures.

2016 moed A, question 2 (30 points). A game engine has SHAPEs (SPHERE, BOX) drawn by SHADERs (BASIC_SHADER, COMPLEX_SHADER). Each shader has Render(SPHERE*) and Render(BOX*). RENDER_MGR::Render loops over shapes and shaders. Overload resolution on a SHAPE* cannot pick Render(SPHERE*).

a. (20) Implement the visitor pattern so the loop dispatches to the right pair. SHAPE and SHADER must be abstract. Add code only in the classes named in the question.

b. (10) Write a deep copy constructor for RENDER_MGR.

Hint 1 of 3

Double dispatch needs two virtual calls: the shape accepts the shader, and the shader then receives the concrete shape.

Hint 2 of 3

Accept on SPHERE calls shader->Render(this) where this is SPHERE*, so the overload is resolved in the derived class.

Hint 3 of 3

A manager that holds owning pointers deep-copies by cloning each shape and each shader, not by copying the pointers.

Solution

struct Shader {
    virtual ~Shader() = default;
    virtual void Render(Sphere* s) = 0;
    virtual void Render(Box* b) = 0;
};
struct Shape {
    virtual ~Shape() = default;
    virtual void Accept(Shader* sh) = 0;
};
struct Sphere : Shape {
    void Accept(Shader* sh) override { sh->Render(this); }
};
struct Box : Shape {
    void Accept(Shader* sh) override { sh->Render(this); }
};

RENDER_MGR::Render calls shape->Accept(shader) for each pair. BasicShader and ComplexShader override both Render overloads. The copy constructor allocates new shapes and shaders. If the hierarchy has a virtual clone(), that is the deep copy; copying the pointer array is the bug part (b) is there to catch.

2016 moed B, question 1 (30 points). SynchQueue implements Queue with every method synchronized on this. ExtIntQueue adds sum() over the integers.

a. (4) Pre- and postcondition of sum. b. (6) An interleaving where the postcondition fails. c. (10) Make sum correct without synchronizing the whole walk, in the optimistic style of a versioned iterator. The method must not stay locked for the whole summation. d. (10) Mystics look at a fork while thinking, and must not look at a fork someone is eating with. Adjust the semaphore protocol from the dining philosophers.

Hint 1 of 3

sum is a query. Its postcondition names the elements present at one instant.

Hint 2 of 3

A synchronized add in the middle of an unsynchronized walk changes the total.

Hint 3 of 3

A version stamp that add and remove increment lets sum retry when the stamp moved.

Solution

a. Precondition: the queue's invariant holds (size matches the chain). Postcondition: the result equals the sum of the integers that were in the queue at one moment during the call, and sum does not change the queue.

c. Keep a volatile int version incremented at the end of every mutator. sum records the version, walks without holding the lock, adds, and retries if the version changed. A bounded number of retries can fall back to a locked walk so the method is wait-free only in the quiet case and still terminates. The walk itself is not inside synchronized.

d. A fork that is being eaten with is held exclusively, as in the philosopher solution. A fork that is only being looked at can be held by many mystics: a reader side of a ReadWriteLock, or a separate count. Eating takes the write side, so it waits until lookers leave, and lookers wait while an eater holds it. Two mystics may look at one fork together. Nobody looks at a fork an eater holds.

2016 moed B, question 3 (30 points). The reactor's executor picks a task with no regard to how many bytes that client has already transferred, and no regard to how many requests that client has already had served. A busy client can be chosen forever.

a. (10) Give one short scenario for each unfairness. b. (20) Implement two policies: prefer the client with the fewest bytes so far, and prefer the client with the fewest requests so far. You may introduce a PriorityBlockingQueue whose order is compareTo at enqueue time. Do not copy the whole reactor.

Hint 1 of 3

The selector thread is not the place to scan every client on each event. The executor's queue is.

Hint 2 of 3

A priority computed only at enqueue goes stale. Say so if you still use that queue.

Hint 3 of 3

Each policy is a comparison key stored on the task: bytes, or request count.

Solution

a. Client A has sent one huge upload and client B has sent a few bytes. If the executor always prefers A, B waits behind a client who has already consumed the most bandwidth. Separately, client A has had a thousand requests and client B has had one. If the queue is FIFO among ready tasks, A stays ahead simply by arriving more often, and B's request count remains the smaller one while A is served again.

b. Put tasks in a queue ordered by the client's byte count, ascending, for the first policy, and by the client's served-request count for the second. The worker takes the minimum. Update the client's counters when a task finishes, and enqueue the next task for that client with the new key. A PriorityBlockingQueue that freezes compareTo at insertion will not move a task when the counter later changes; either re-enqueue, or document that the key is the count at enqueue, which still prevents a brand-new heavy client from jumping a client who has been waiting with a low count. class SmartPointer {
    T* ptr_;
    int* count_;
public:
    explicit SmartPointer(T* p) : ptr_(p), count_(new int(1)) {}
    SmartPointer(const SmartPointer& other) : ptr_(other.ptr_), count_(other.count_) {
        ++*count_;
    }
    ~SmartPointer() {
        if (--*count_ == 0) {
            delete ptr_;
            delete count_;

        ptr_ = other.ptr_;

        ++*count_;
        return *this;

    T& operator*() const { return *ptr_; }
    T* operator->() const { return ptr_; }

    private int arrived;
    private int generation;
    public Barrier(int parties) { this.parties = parties; }

            generation++;
            notifyAll();
            return 0;
        }
        while (g == generation) wait();

Hint 1 of 3

A raw clone() that always allocates never shares. The sharing has to be in the wrapper, with a count of readers.

Hint 2 of 3

on_write clones only when the count is greater than one, then drops this wrapper off the old count.

Hint 3 of 3

Before any write, one A on the heap and two wrappers pointing at it. After b writes, two A objects.

Solution

template <typename T>
class copy_on_write {
public:
    T* ptr;
    int* users;
    explicit copy_on_write(T* p) : ptr(p), users(new int(1)) {}
    copy_on_write(const copy_on_write& o) : ptr(o.ptr), users(o.users) { ++*users; }
    void on_write() {
        if (*users > 1) {
            --*users;
            ptr = ptr->clone();
            users = new int(1);
        }
    }
    ~copy_on_write() {
        if (--*users == 0) { delete ptr; delete users; }
    }
};

2024 moed C, question 2 (30 points). Set adds iterator() and clone() to contains and add. SetImpl is a linked list. An iterator that walks next pointers races with add. Make iterator and add safe. Cloning must not publish a structure another thread is in the middle of changing.

Hint 1 of 3

A fail-fast iterator remembers a version. add increments it.

Hint 2 of 3

clone must copy the nodes while holding the same lock add holds, or the copy tears.

Hint 3 of 3

ConcurrentModificationException is the usual signal. Returning a snapshot is the other legal design.

Solution

One lock around add, contains, iterator's creation, and clone. add appends a node and increments modCount. The iterator copies modCount at creation and throws ConcurrentModificationException if it changes before next. That is the fail-fast contract.

clone holds the lock, walks the list, and allocates a new list with the same elements. The returned set has its own nodes and its own lock. Callers who use the clone do not share structure with the source. A snapshot iterator, which copies the elements at iterator() time, is the alternative that does not fail fast and also needs the lock only during the copy.
