תוכנית C++ לא מקבלת שק אחד אחיד של זיכרון. לתהליך יש מרחב כתובות משלו, והשפה שמה את הקוד, את המשתנים הגלובליים, את מסגרות הקריאה ואת הבלוקים של `new` באזורים שונים בתוכו. כל ציור בהמשך הקורס — מצביע (pointer) על המחסנית (stack), חוצץ על הערימה (heap), ארגומנט שמועבר לפי ערך — הוא ציור של האזורים האלה.

Java, C# ו-Python מסתירות את אותה מכונה. הזיכרון אצלן מנוהל, והשחרור אוטומטי: Garbage Collector. ב-C++ המפתחות אצל המתכנת. `new` הוא קבלת מפתח לדירה, ו-`delete` הוא החזרת המפתח. מי ששוכח להחזיר את המפתח משאיר את הדירה שכורה, וזו זליגת זיכרון.

## סביבת זמן ריצה

הסיכומים של אדלר פותחים לפני חמשת האזורים. השאלה שם היא למה תוכנית לא פונה אל המעבד בעצמה. הדוגמה היא מערכת שמחפשת סרט, מורידה אותו, ומקרינה אותו. חיפוש ברשת, עבודה עם קבצים, ופענוח של הווידאו הם שלושה שירותים. המעבד לבדו לא נותן אף אחד מהם בנוחות. מישהו צריך לשבת בין התוכנית לחומרה.

:::definition id=def-runtime title="מחשב, תוכנית, תהליך, וסביבת זמן ריצה" source="Notes/lecture-notes.docx.pdf"
מחשב (computer) הוא יחידה לוגית שמבצעת משימה בעצמה, באמצעות ערכת הפעולות שלה. תוכנית (program) היא הגדרה פורמלית של משימה. תהליך (process) הוא תוכנית בזמן שמחשב מריץ אותה.

סביבת זמן ריצה (runtime environment) מתווכת בין התוכנית לתשתית. יש לה ארבעה תפקידים: היא משמרת את תכונות התשתית, היא מוסיפה הפשטה, היא נותנת ממשק נוח יותר אל התשתית, והיא נותנת שירותים שאין לתשתית עצמה.
:::

מערכת ההפעלה היא סביבת זמן הריצה הראשונה בסיכומים. היא יושבת בין התהליך לחומרה. כשמריצים תוכנית, מערכת ההפעלה בונה את התהליך, ואז מזיזה אותו בין המצבים. מונה התוכנית (program counter, PC) הוא הכתובת של השורה הבאה שהמעבד יבצע.

:::definition id=def-process-states title="מצבי תהליך" source="Notes/lecture-notes.docx.pdf"
לתהליך יש חמישה מצבים:

| מצב | מה נכון עכשיו | לאן עוברים |
| --- | --- | --- |
| Created | נבנה אובייקט התהליך, הוקצה זיכרון, נטען הקובץ, וה-PC מצביע על השורה הראשונה של `main` | Runnable |
| Runnable | יכול לרוץ, וממתין לתור של המתזמן | Running |
| Running | רץ בפועל. כל צעד מעביר את ה-PC לשורה הבאה | Runnable כשנגמרה הקצאת הזמן; Blocked כשיש אילוץ, למשל קריאה מהרשת; Terminated כשהתוכנית נגמרה |
| Blocked | אינו יכול לרוץ, ואינו בתור | Runnable כשהאילוץ הוסר |
| Terminated | המשאבים נוקו והתהליך שוחרר | אין |

:::

![חמישה מצבי תהליך: Created נכנס ל-Runnable, Runnable ו-Running מחליפים תור, Running יורד ל-Blocked וחוזר, ו-Running מסיים ב-Terminated](../assets/figures/process-states.svg)

קריאת מערכת (system call) היא הדרך שבה תהליך מבקש שירות מהחומרה. זו קריאה לפונקציה שמערכת ההפעלה מספקת. התהליך לא נוגע בכרטיס בעצמו. אירוע שמגיע מהחומרה חוזר אל התהליך כהודעה ממערכת ההפעלה.

מערכת ההפעלה עושה עוד שלושה דברים. היא מריצה יותר תהליכים ממספר המעבדים, ומחליפה ביניהם. היא נותנת לתהליך מרחב כתובות גדול יותר מה-RAM הפיזי. היא שומרת הרשאות קריאה וכתיבה על קבצים.

המכונה הווירטואלית של Java היא סביבת זמן ריצה שנייה, מעל מערכת ההפעלה. הפרק [חזרה ל-Java](topic:java-runtime) פורש איך אותו בייטקוד רץ על מערכות הפעלה שונות.

## חמשת האזורים

פרק 1 מצייר את מרחב הכתובות מכתובות גבוהות כלפי מטה, אל כתובות נמוכות. השמות בשקפים הם השמות שכדאי לשמור.

:::definition id=def-address-space title="מרחב הכתובות של תהליך" source="Classes/Chapter 1 - The Memory Model.pptx"
לתהליך רץ יש טווח כתובות משלו. בתוך הטווח הזה הקורס מפריד חמישה אזורים:

| אזור | השם בשקפים | גודל | מי משחרר | גישה |
| --- | --- | --- | --- | --- |
| מחסנית | stack | גדל וקטן | אוטומטית, LIFO | קריאה וכתיבה |

| קוד | text | קבוע | משך חיי התהליך | קריאה בלבד |

כתובות גבוהות יושבות בקצה המחסנית של הציור. כתובות נמוכות יושבות בקוד.
:::

![מרחב הכתובות של התהליך, כתובות גבוהות למעלה: מחסנית, ערימה, משתנים לא מאותחלים, משתנים מאותחלים, וקוד](../assets/figures/address-space.svg)

המחסנית מחזיקה את המשתנים המקומיים, ואת מה שהקריאה צריכה כדי לחזור אל מי שקרא. כשהפונקציה חוזרת, המסגרת נשלפת, והבתים של המקומיים נעלמים איתה.

הערימה מחזיקה בלוקים של `new`. הבלוק לא יושב בתוך המסגרת של הפונקציה שקראה ל-`new`. הוא יכול להמשיך להתקיים אחרי שהפונקציה הזו חזרה.

שני האזורים הסטטיים מחזיקים משתנים שקיימים כל עוד התהליך רץ. אזור הקוד מחזיק את הוראות המכונה. התוכנית קוראת את ההוראות. היא לא כותבת אליהן.

![מכונת פון נוימן (Von Neumann): מעבד (CPU), bus, ו-RAM אחד שמחזיק גם את התוכנית וגם את הנתונים](../assets/figures/von-neumann-architecture.svg)

### משתנים סטטיים

משתנה סטטי מאותחל רק בערך שהקומפיילר (compiler) יכול לחשב, לא בקריאה לפונקציה. בשקפים מופיעות שלוש צורות:

```cpp
int a = 1;                 // global: whole run, visible from every file
static int b = 2;          // file-scope static: whole run, this file only
void function() {
    static int c = 3;      // function static: whole run, this function only
}                          // c is initialized once, not on every call
```

אפשר לנקוב ב-`a` מכל קובץ שמצהיר עליו. ב-`b` אפשר לנקוב רק מתוך הקובץ שבו הוא מוגדר. `c` שומר את הערך שלו בין קריאות. רק `function` יכולה לנקוב ב-`c`.

בדוגמה הבאה, ל-`c` ול-`x` אין אותו זמן חיים, אף על פי ששניהם נכתבים בתוך `tick`. `c` יושב באזור הסטטי, והאתחול שלו רץ פעם אחת. `x` יושב במסגרת, ויש `x` חדש בכל קריאה. `tick` מאתחלת את `c` פעם אחת, ואז סופרת.

```cpp
void tick() {
    static int c = 0;   // static region, initialized on the first call
    int x = c;          // stack, a new x on every call
    c = c + 1;
}

int main() {
    tick();             // x is 0, then c becomes 1, then x is gone
    tick();             // x is 1, copied from the c that stayed
}
```

| רגע | `c` | `x` |
| --- | --- | --- |
| הקריאה הראשונה, בשורת `int x = c` | 0 | 0 |
| הקריאה הראשונה, בחזרה | 1 | נעלם |
| הקריאה השנייה, בשורת `int x = c` | 1 | 1 |

![c נשאר באזור הסטטי אחרי החזרה. הקריאה השנייה מקבלת x חדש שקורא את ה-c שנשאר](../assets/figures/static-calls.svg)

### מסגרת המחסנית

:::definition id=def-stack-frame title="מסגרת מחסנית" source="Classes/Chapter 1 - The Memory Model.pptx"
מסגרת מחסנית, שנקראת גם מסגרת הפעלה (activation frame), נדחפת בכל קריאה לפונקציה. היא מחזיקה את כתובת החזרה, את הפרמטרים שהועברו, ואת המשתנים המקומיים. המסגרות יוצאות בסדר LIFO כשהקריאה חוזרת.
:::

משתנה מקומי יושב במסגרת שנדחפת עם הקריאה ונשלפת עם החזרה. השפה משחררת אותו בעצמה, בלי חיפוש של מקום פנוי. לכן התא שלו זול. הוא גם נעלם כשהפונקציה חוזרת, כי הבתים שלו היו חלק מהמסגרת.

מילוי המחסנית (stack overflow) הוא מצב שבו אין מקום למסגרת נוספת. הדוגמה בשקף היא רקורסיה אינסופית. `forever`, בהמשך הפרק, מציירת את זה.

זו הקריאה שהציור מתאר. `foo(a)` מעתיקה את הערך של `a` לפרמטר חדש. היא לא מוסרת ל-`foo` את המשתנה `a` עצמו.

```cpp
void foo(int n) {
    int x = n * 2;
}

int main() {
    int a = 4;
    foo(a);
    return 0;
}
```

בזמן ש-`foo` על מחסנית הקריאות קיימות שתי מסגרות. `main` עדיין מחזיקה את `a`. `foo` מחזיקה את כתובת החזרה, את הפרמטר `n`, ואת המשתנה המקומי `x`. החזרה שולפת רק את `foo`.

| שם | בזמן ש-`foo` רצה | אחרי ש-`foo` חוזרת |
| --- | --- | --- |
| `a` | המסגרת של `main`, הערך 4 | עדיין במסגרת של `main`, עדיין 4 |
| `n` | המסגרת של `foo`, הערך 4 | נעלם עם המסגרת |
| `x` | המסגרת של `foo`, הערך 8 | נעלם עם המסגרת |
| כתובת חזרה | המסגרת של `foo`, מצביעה חזרה אל `main` | בשימוש, ואז נעלמת |

![בזמן ש-foo רצה, n ו-x יושבים במסגרת של foo מתחת ל-main. אחרי החזרה נשארות רק המסגרת של main, ו-a](../assets/figures/stack-frames.svg)

:::problem id=worked-frame-call title="מסגרת של קריאה" source="Classes/Chapter 1 - The Memory Model.pptx" kind=worked solution_origin=source
איפה `n` ו-`x` חיים בזמן ש-`foo` רצה, ומה נשאר אחרי ש-`foo` חוזרת?

```cpp
void foo(int n) {
    int x = n * 2;
}

int main() {
    int a = 4;
    foo(a);
    return 0;
}
```

:::solution
`n` ו-`x` חיים שניהם במסגרת המחסנית של `foo`. `n` הוא הפרמטר, עותק של ה-4 ש-`main` העבירה. `x` הוא המשתנה המקומי, והוא 8. המסגרת הזו יושבת מתחת למסגרת של `main`, שעדיין מחזיקה את `a`.

החזרה שולפת את המסגרת של `foo`, ולכן השמות `n` ו-`x` לא קיימים אחר כך. `a` לא נגע, כי הקריאה העתיקה את הערך ולא כתבה דרך `a`.

`new` בתוך `foo` הוא החריג. הבלוק על הערימה, ורק המצביע אליו שבמסגרת נעלם.
:::
:::

:::check id=chk-frame-gone
אחרי ש-`foo` חוזרת, איזה מהשמות האלה עדיין קיים?

```cpp
void foo(int n) {
    int x = n * 2;
}
int main() {
    int a = 4;
    foo(a);
}
```

- [ ] `n`, כי הפרמטר הועבר פנימה
- [ ] `x`, כי הוא אותחל
- [x] רק `a`

`n` ו-`x` היו תאים במסגרת שהחזרה שלפה. `a` נמצא ב-`main`, ו-`main` עוד לא חזרה.
:::

### הערימה

```cpp
int* pi = new int;       // one int on the heap; pi itself is local
delete pi;

int* arr = new int[10];  // ten ints on the heap
delete[] arr;            // the array form, not delete
```

השקף מציין יתרון שנשמע מוזר במבט ראשון: לערימה אין שחרור אוטומטי. זה יתרון, כי הבלוק יכול להמשיך לחיות אחרי שהפונקציה שקראה ל-`new` כבר חזרה. משתנה מקומי לא יכול לעשות את זה. הוא נעלם עם המסגרת.

המחיר הוא זמן, וגם רישום. `new` פונה למערכת ההפעלה ומחפש מקום פנוי, ולכן ההקצאה איטית יותר מתא שכבר יושב במסגרת. הערימה צריכה רישום (book keeping) של התאים המוקצים ושל התאים הפנויים. במחסנית אין רישום כזה. המסגרת האחרונה שנדחפה היא תמיד זאת שמשתחררת.

המצביע והבלוק לא יושבים באותו אזור.

```cpp
int* pi = new int[10];     // pi on the stack, the ten ints on the heap
Student* ps = new Student("Avi");  // ps on the stack, the Student on the heap
```

בדוגמה הראשונה, `pi` הוא משתנה מקומי. הבתים של `pi` עצמו, זאת אומרת הכתובת, יושבים במסגרת על המחסנית. עשרת ה-`int` יושבים על הערימה, בבלוק ש-`new[]` הקצה. בדוגמה השנייה אותו פיצול: `ps` על המחסנית, ואובייקט ה-`Student` על הערימה.

האם יכולה להיות זליגת זיכרון מהמחסנית? המסגרת נשלפת כשהפונקציה חוזרת, והמצביע המקומי נעלם יחד איתה. זה התפקיד של המחסנית. היא לא משאירה אחריה את המשתנים המקומיים.

זליגת הזיכרון, כשיש כזאת, יושבת על הערימה. הבלוק נשאר מסומן כמוקצה, ואין בתוכנית שם שמחזיק את הכתובת שלו. `leaky` למטה מציירת את זה. הסעיף "למה הפיצול בנוי כך" הולך על אותה דוגמה צעד אחר צעד.

ב-Java, ה-Garbage Collector משחרר אובייקט (object) שלא נשארו אליו רפרנסים (reference). מה שנקרא שם זליגת זיכרון הוא רפרנס שעדיין אפשר להגיע אליו, ושהתוכנית שכחה להשתמש בו. זו תקלה אחרת מ-`delete` חסר ב-C++.

```cpp
void leaky() {
    int* box = new int(9);   // box is a stack slot, 9 is an int on the heap
}                            // the return pops box and does not call delete
```

![בתוך leaky מצביע המחסנית מצביע אל ה-int שעל הערימה. אחרי החזרה ה-int עדיין שם, ושום דבר לא מצביע אליו](../assets/figures/heap-leak.svg)

### תוכנית אחת, חמישה בתים

אותה ריצה יכולה לגעת בכל אזור בבת אחת. קראו את זה בקריאה השנייה של `note`, בשורה שאחרי `new` ולפני `delete`.

```cpp
int ready = 1;              // initialized static, whole run
int scratch;                // uninitialized static, whole run

void note() {
    static int calls = 0;   // initialized static, once
    int x = calls;          // local on the stack
    int* box = new int(x);  // box on the stack, the int on the heap
    calls = calls + 1;
    delete box;
}

int main() {
    note();                 // x becomes 0, calls becomes 1, box is gone
    note();                 // x becomes 1, from the calls that stayed
}
```

![הקריאה השנייה של note: x ו-box על המחסנית, ה-int החדש על הערימה, calls ו-ready באחסון הסטטי, ההוראות בקוד](../assets/figures/five-homes.svg)

| שם | אזור | חי אחרי ש-`note` חוזרת |
| --- | --- | --- |
| `ready` | משתנים מאותחלים | כן, עד שהתהליך נגמר |
| `scratch` | משתנים לא מאותחלים | כן |
| `calls` | משתנים מאותחלים | כן, והוא שומר את המונה |
| `x` | מסגרת המחסנית של `note` | לא |
| `box` | מסגרת המחסנית של `note` | לא |
| ה-`int` מ-`new` | ערימה | רק עד `delete box` |
| ההוראות | אזור הקוד | כן, והתוכנית לא כותבת אותן |

### רקורסיה מוציאה מסגרות, לא ערימה

כל קריאה רקורסיבית דוחפת עוד מסגרת. המסגרת הקודמת נשארת במקומה, כי הקריאה ההיא עוד לא חזרה.

ב-`forever`, `main` קוראת ל-`forever(0)`. `forever` קוראת לעצמה עם `n + 1`. אף אחת מהקריאות האלה לא מגיעה לשורה שאחרי הקריאה הרקורסיבית, ולכן אף מסגרת לא נשלפת. `pad` הוא מערך של 256 ערכי `int` בתוך כל מסגרת. כל קריאה חדשה מוסיפה עוד מערך כזה. הבתים האלה מצטברים על המחסנית, עד שהאזור מלא.

```cpp
void forever(int n) {
    int pad[256];
    forever(n + 1);    // this call does not return, so no frame is popped
}

int main() {
    forever(0);
}
```

![forever ממשיכה לדחוף מסגרת עבור n ו-pad. המחסנית גדלה כלפי מטה עד שהאזור מלא](../assets/figures/recursion-frames.svg)

הערימה בתוכנית הזו לא מקבלת אף `new`. היא נשארת ריקה. המילוי הוא של המחסנית, וזו דוגמת ההרצאה למילוי המחסנית. הערימה היא הצד שנשאר תקין, כי לא הוקצה עליה כלום.

אפשר למלא את הערימה בלי למלא את המחסנית. פונקציה אחת שכן חוזרת, ובתוכה לולאה שקוראת רק ל-`new`, דוחפת מסגרת אחת. מצביע המחסנית (stack pointer) זז החוצה עבור הקריאה הזאת, וחוזר כשהפונקציה חוזרת. העומק נשאר מסגרת אחת. כל סיבוב של הלולאה מקצה עוד בלוק על הערימה. הערימה היא מה שמתמלא.

"נשארת בעומק של מסגרת אחת" מתאר את תנועת המצביע. המשפט מתאר את עומק המחסנית. הוא לא אומר שהתוכנית נכונה.

## למה הפיצול בנוי כך

למסגרת קריאה יש זמן חיים מקונן. כשפונקציה אחת קוראת לפונקציה אחרת, המסגרת של הפונקציה שנקראה חיה כולה בתוך זמן החיים של המסגרת של הפונקציה שקראה. המסגרת הפנימית חייבת להיגמר לפני שהחיצונית יכולה להיעלם.

בדוגמה של `note`, `main` קוראת ל-`note`. מרגע הקריאה יש שתי מסגרות. המסגרת של `main` כבר שם. המסגרת של `note` נדחפה בגלל הקריאה. המסגרת של `note` חיה בתוך זמן החיים של `main`. `note` חייבת לחזור לפני שהמסגרת של `main` יכולה להיעלם. כל עוד הקריאה ל-`note` עוד לא חזרה, אי אפשר לשלוף את `main`.

המסגרת שנעלמת היא תמיד החדשה ביותר. ב-`forever` אף קריאה לא חוזרת, ולכן כל מסגרת חדשה נשארת. בציור היא נמצאת מתחת לקודמת, כי המחסנית גדלה כלפי מטה. הערימה נשארת ריקה. ברגע שקריאה כן חוזרת, נשלפת רק המסגרת האחרונה שנדחפה. סדר כזה הוא מחסנית. לכן מסגרות קריאה יושבות על מחסנית.

ההקצאה של מסגרת היא הזזה של מצביע אחד. מצביע המחסנית מסמן את הקצה של המסגרת האחרונה שנדחפה. כדי לפתוח מסגרת מזיזים אותו בגודל המסגרת. כדי לסגור אותה מזיזים אותו חזרה, לאותו מקום. ההקצאה לא מחפשת תא פנוי. השחרור לא משאיר חור באמצע. הסיבה היא שאי אפשר לשחרר מסגרת ישנה כל עוד מסגרת חדשה יותר עוד לא נשלפה. תמיד משתחררת האחרונה שנדחפה.

כך זה נראה בקריאה ל-`note`. לפני הקריאה יש על המחסנית רק את המסגרת של `main`. הקריאה מזיזה את מצביע המחסנית ודוחפת את המסגרת של `note`. בציור המסגרת הזו נמצאת מתחת למסגרת של `main`, כי המחסנית גדלה אל הכתובות הנמוכות. היא המסגרת האחרונה שנדחפה, ולכן היא זאת שיוצאת ראשונה. כש-`note` חוזרת, המצביע זז חזרה. המסגרת של `note` נעלמת. נשארת המסגרת של `main`, עם המשתנים שלה.

יש שני מקרים שבהם הבתים לא יכולים לשבת במסגרת. כל מקרה הוא סיבה בפני עצמו.

המקרה הראשון הוא אובייקט שחייב להמשיך להתקיים אחרי שהפונקציה חוזרת. משתנה מקומי נעלם יחד עם המסגרת. ה-`int` ש-`new` מקצה הוא לא מקומי. הבתים שלו יושבים על הערימה. הכתובת של הבלוק יכולה לחזור מהפונקציה, או להישמר במקום שממשיך לחיות אחרי הקריאה. אחרי החזרה הכתובת עדיין מצביעה על בתים קיימים. אם ה-`int` היה משתנה מקומי, החזרה הייתה מוחקת את הבתים יחד עם המסגרת. הכתובת הייתה נשארת, והבתים שהיא מצביעה אליהם כבר לא היו שם.

המקרה השני הוא גודל שלא ידוע כשהמסגרת נבנית. `new int[n]`, כש-`n` מגיע מהקלט, מבקש מערך שהגודל שלו מתברר רק בזמן הריצה. הגודל של מסגרת קבוע לאותה קריאה. הקומפיילר יודע מראש איפה כל מקומי יושב בתוך המסגרת, ולכן הוא לא משאיר בה חור שהגודל שלו ייקבע אחר כך. בלוק על הערימה יכול להיות בכל גודל שבוחרים בזמן הריצה. `new` מקבל את מספר התאים כפרמטר, ומסמן סדרה רצופה כמוקצית.

למחסנית יש סוף שהשפה מכירה. החזרה מהפונקציה היא הסוף הזה, והמסגרת משתחררת לבד. לערימה אין סוף אוטומטי. הבלוק לא קשור למסגרת שביקשה אותו. הקריאה ל-`delete` היא הדרך של המתכנת לומר שהשימוש האחרון נגמר. בלי הקריאה הזו הבלוק נשאר מסומן כמוקצה.

המשפט "המחסנית בסדר ויש זליגת זיכרון" מדבר על `leaky`, ועל הציור שמופיע לידה. `box` הוא מצביע מקומי. הוא יושב במסגרת המחסנית של `leaky`. `new int(9)` מקצה על הערימה בלוק של `int` אחד. הערך בתוך הבלוק הוא 9. הכתובת של הבלוק נשמרת ב-`box`.

כש-`leaky` חוזרת, המסגרת נשלפת. זה מה שצריך לקרות. משתנים מקומיים אמורים להיעלם עם המסגרת. המחסנית לא התמלאה. החזרה גם לא קלקלה מסגרת אחרת. היא שלפה רק את המסגרת של `leaky`. "המחסנית בסדר" אומר שהמחסנית עשתה את העבודה שלה.

הבלוק שעל הערימה לא נשלף. זמן החיים שלו לא קשור למסגרת. העותק היחיד של הכתובת ישב בתוך `box`, ו-`box` כבר איננו. הבלוק עדיין מסומן כמוקצה. אין בתוכנית משתנה שמחזיק את הכתובת, ולכן אי אפשר לקרוא ל-`delete` על הבלוק. הבלוק הזה, שנשאר בלי כתובת שמגיעה אליו, הוא זליגת הזיכרון. הבאג יושב על הערימה: נשאר בלוק שאף אחד לא יכול להצביע אליו.

שני המצבים הבאים מראים איזה אזור מתמלא. הם נפרדים מהזליגה של `leaky`.

`forever` לא חוזרת. כל קריאה דוחפת עוד מסגרת, עם `n` ועם `pad`. המחסנית מתמלאת. זו מילוי המחסנית. הערימה לא בשימוש, והיא הצד שנשאר תקין.

לולאה שקוראת רק ל-`new`, בתוך פונקציה אחת שכן חוזרת, עושה את ההפך. נדחפת מסגרת אחת. מצביע המחסנית זז החוצה עבור הקריאה, וחוזר כשהפונקציה חוזרת. המחסנית נשארת בעומק של מסגרת אחת. הערימה היא מה שמתמלא, בלוק אחד לכל סיבוב.

"נשארת בעומק של מסגרת אחת" מתאר את תנועת המצביע. המשפט מתאר את עומק המחסנית. הוא לא אומר שהתוכנית נכונה.

אזור הקוד, בטבלה של מרחב הכתובות, הוא אזור נפרד. הגישה אליו היא קריאה בלבד. ההוראות שהמעבד יביא בצעדים הבאים יושבות שם. כתיבה שגויה אל נתון, במחסנית או בערימה או במשתנה סטטי, נוגעת באזור אחר. היא לא משכתבת את ההוראות.

בטבלה הזו, הגודל של האזורים הסטטיים קבוע בזמן הקומפילציה. הכתובת של כל משתנה סטטי קבועה גם היא. המילה קבועים כאן מתארת את הכתובת ואת הגודל של האזור. היא לא אומרת שהערך הוא `const`. ב-`note`, `calls` משנה את הערך שלו: בקריאה הראשונה הוא עולה מאפס לאחד, ובקריאה השנייה `x` קורא את האחד שנשאר. מה שלא זז הוא המקום של `calls` בזיכרון.

המקשר (linker) נותן למשתנים הסטטיים את המקום הזה לפני ש-`main` מתחילה. הם לא נוצרים מקריאה לפונקציה, ולכן אין מסגרת שצריכה להקצות אותם בכל קריאה.

`delete` ו-`delete[]` הן שתי צורות של שחרור, וכל אחת הולכת עם צורת הקצאה משלה. `new` מקצה אובייקט אחד, ו-`delete` משחרר אובייקט אחד. `new[]` מקצה מערך, ו-`delete[]` משחרר מערך.

השקף אומר שהערימה דורשת רישום. הסיכומים מפרטים את הרישום הזה. לכל תא בערימה יש סימון: מוקצה, או לא מוקצה. `new` מסמן סדרת תאים רצופים כמוקצים. `delete` אמור לסמן את הסדרה שהוקצתה כלא מוקצית, כדי שההקצאה הבאה תוכל למצוא אותה פנויה.

ערבוב הצורות פוגע ברישום. `delete` על מערך שהוקצה ב-`new[]` משחרר אובייקט אחד, אבל הבלוק שהמצביע מחזיק הוא מערך. `delete[]` על אובייקט שהוקצה ב-`new` משחרר מערך, אבל הבלוק הוא אובייקט אחד. השחרור לא מתאים להקצאה. אחרי שחרור כזה, הסימון של מה שתפוס ומה שפנוי כבר לא מתאר את הערימה. "הערימה נפגמת" אומר שהרישום עצמו נהרס.

זליגת זיכרון היא תקלה אחרת. בזליגה הכתובת אבדה, והרישום נשאר עקבי: הבלוק עדיין מסומן כמוקצה. ב-`delete` שאינו מתאים להקצאה, הכתובת עוד בידינו. הרישום הוא מה שנפגם.

## המכונה שמתחת לאזורים

אותו RAM מחזיק גם את ההוראות וגם את הנתונים. זו ארכיטקטורת פון נוימן: זיכרון אחד, יחידת עיבוד מרכזית, וערוץ העברת נתונים ביניהם.

:::definition id=def-von-neumann title="מכונת פון נוימן" source="Classes/Chapter 1 - The Memory Model.pptx"
המכונה בהרצאה היא מעבד, ערוץ העברת נתונים, ו-RAM. טקסט התוכנית והנתונים יושבים שניהם ב-RAM הזה. המעבד חוזר על מחזור הבאה-פענוח-ביצוע (fetch-decode-execute): מביא הוראה מהזיכרון, מפענח אותה, ומבצע אותה.
:::

בתוך המעבד ההרצאה מונה ארבעה רכיבים, ועוד השעון:

- יחידת הבקרה (control unit, CU) מביאה הוראה מהזיכרון, מפענחת אותה, ומבצעת אותה. היא משתמשת בשעון (clock) כדי להישאר מסונכרנת. היא מטפלת בקלט ובפלט דרך פסיקות (interrupts).
- יחידת החישוב (ALU) עושה אריתמטיקה של שלמים. היא גם משווה ערכים, עושה פעולות על סיביות (bitwise), ובודקת חריגות (overflow).
- אוגרים (registers), גם רגיסטרים, הם האחסון המהיר ביותר. אוגרים כלליים מחזיקים ערכים להוראות רגילות כמו load ו-save. אוגרים ייעודיים כוללים את מצביע ההוראה `ip`. אוגרים משולבים כוללים את `rsp`. `rsp` הוא מצביע המחסנית: הוא מסמן את הקצה של המסגרת האחרונה שנדחפה. הוראות כמו `push`, `pop` ו-`jump` משתמשות באוגרים המיוחדים האלה.
- זיכרון מטמון (cache) יושב בין האוגרים ל-RAM. L1 הוא הקטן והמהיר ביותר, ואחר כך L2, ואחר כך L3. כל רמה גדולה יותר ואיטית יותר מזו שלפניה. השעון קובע כמה צעדים המעבד עושה בשנייה.

![רכיבי המעבד בטבלה, ואחר כך זיכרון המטמון, ערוץ העברת הנתונים, ו-RAM, עם היררכיית הזיכרון המהירה למעלה](../assets/figures/memory-hierarchy.svg)

כשהמעבד טוען משתנה מקומי, הכתובת שהוא קורא יושבת במחסנית. כשהוא טוען דרך `pi`, הכתובת יושבת בערימה. שתי הקריאות נוסעות על ערוץ העברת הנתונים. האזורים הם מוסכמה של התוכנה מעל RAM אחד.

הסיכומים מפרידים את אותו זיכרון לשלוש נקודות מבט. החומרה רואה טכנולוגיות. מערכת ההפעלה רואה הקצאה לתהליך. השפה רואה מחסנית, ערימה, משתנים, אובייקטים וירושה. הטבלה של החומרה, לפי גודל, מהירות, מחיר, והאם המידע שורד בלי חשמל:

| רכיב | בשביל מה | שורד בלי חשמל |
| --- | --- | --- |
| רגיסטר | הערך של הפעולה הנוכחית, ומה שהמעבד צריך כל הזמן | לא |
| מטמון | עותק של תאי RAM שנקראו לאחרונה, כדי לא לרדת ל-RAM בכל צעד | לא |
| RAM | המידע של התהליך בזמן הריצה | לא |
| דיסק | מה שהמשתמש צריך אחרי שהתהליך נגמר | כן |
| טייפ | גיבוי | כן |

הכלל שם: האחסון המהיר קטן ויקר, והאחסון הגדול איטי וזול.

רוחב אפיק הנתונים (data bus) הוא כמה ביטים עוברים בפעולת זיכרון אחת. המספר הזה הוא גודל המילה. רוחב אפיק הכתובות (address bus) קובע כמה זיכרון המעבד יכול לנקוב בשמו. רכיב RAM יכול להיות גדול יותר מהטווח שהאפיק מגיע אליו. מה שמעבר לטווח אינו נגיש למעבד הזה.

למעבד יש ערכת הוראות (instruction set). `ADD R1 R2 R3` מחבר את הרגיסטרים `R1` ו-`R2` ושם את הסכום ב-`R3`. `READ 100 R1` מעתיק את תא 100 אל `R1`. `WRITE R2 200` מעתיק את `R2` אל תא 200. השפה מתורגמת אל שלוש ההוראות האלה.

:::problem id=worked-add-trace title="עקבות של חיבור" source="Notes/lecture-notes.docx.pdf" kind=worked solution_origin=source
`i` יושב בתא 3000 ו-`j` בתא 4000. תרגם את שלוש השורות להוראות `READ`, `WRITE` ו-`ADD`.

```java
int i = 10;
int j = 20;
i = i + j;
```

:::solution
קודם נכתבים שני הערכים. אחר כך שניהם נקראים לרגיסטרים, מחוברים, והסכום נכתב חזרה אל התא של `i`. `j` נשאר 20.

```text
WRITE 3000 10
WRITE 4000 20
READ  3000 R1
READ  4000 R2
ADD   R1 R2 R3
WRITE 3000 R3
```

אחרי השורה האחרונה תא 3000 מחזיק 30. החיבור עצמו אינו קורה ב-RAM. הוא קורה ברגיסטר `R3`, ורק אחר כך יוצא אל התא של `i`.
:::
:::

הסיכומים שמים מעל ההוראות האלה מודל של מחסנית ושל ערימה. הקומפיילר הוא מי שמתרגם את הקוד אל הפעולות של המודל.

למחסנית יש שש פעולות. `createAF` פותח אזור חדש. זו מסגרת ההפעלה. `removeAF` חוזר לאזור הקודם, המסגרת של מי שקרא. `push` מוסיף תא אחד בראש המסגרת הנוכחית. `pop` מסיר את התא שבראש. `read` ו-`write` קוראים וכותבים תא בתוך המסגרת הנוכחית. דרכן אי אפשר לגעת בתא של מסגרת אחרת.

לערימה יש ארבע פעולות. `new` מקצה סדרת תאים רצופים, ומסמן אותם כמוקצים. מספר התאים הוא פרמטר, ולכן הוא יכול להתברר בזמן הריצה. `delete` משחרר סדרה כזאת, ומסמן את התאים כלא מוקצים. `read` ו-`write` מותרים רק על תא שכבר מסומן כמוקצה. קריאה או כתיבה לתא פנוי היא שגיאת זמן ריצה.

התרגום של קוד לפעולות האלה הולך לפי סדר. הגדרת משתנה היא `push`, לפי גודל שידוע בזמן הקומפילציה. סוף הבלוק הוא `pop` לכל משתנה שהוגדר בתוכו. קריאה לפרוצדורה מתחילה ב-`createAF`. אחר כך נדחפת כתובת החזרה, כדי שהפרוצדורה תדע לאן לחזור. אם זו מתודה, נדחף גם `this`, הכתובת של האובייקט. אחר כך `push` לכל ארגומנט. בסיום נכתב ערך החזרה למקום זמני. אחר כך `pop` לארגומנטים. אחר כך `removeAF`. בסוף מונה התוכנית חוזר לכתובת החזרה.

מידע שהגודל שלו ידוע רק בזמן הריצה לא נכנס למסגרת. המסגרת כבר נבנתה בגודל קבוע. המידע הזה מוקצה ב-`new` על הערימה, והמתכנת קורא ל-`delete` כשהוא לא נדרש עוד.

מסגרת זולה כי `push` ו-`pop` עובדים בקצה. לא נשאר חור באמצע המחסנית, כי מה שהשתחרר הוא תמיד מה שהוקצה אחרון. הערימה משאירה חור כשמשחררים בלוק בין בלוקים שעדיין חיים: ההקצאה הבאה צריכה לחפש מקום פנוי. כשמפספסים את ה-`delete`, הבלוק נשאר מסומן כמוקצה, ואין מצביע אליו. זו הזליגה ש-`leaky` מציירת. הסעיף הבא מצייר קריאה אחת מהפיצול הזה: `pi` על המחסנית, והמערך על הערימה.

:::check id=chk-where-array
השורה הזו רצה בתוך פונקציה. איפה חיים `pi` ועשרת השלמים?

```cpp
int* pi = new int[10];
```

- [ ] שניהם על המחסנית
- [x] `pi` על המחסנית ועשרת השלמים על הערימה
- [ ] שניהם על הערימה
- [ ] `pi` חי באזור הקוד

משתנה המצביע הוא מקומי, ולכן הוא חלק מהמסגרת. `new` משיג בלוק נפרד שזמן החיים שלו אינו המסגרת.
:::

## פריסה לדוגמה

קחו את שתי השורות מההרצאה וקריאה אחת.

```cpp
int* pi = new int[10];
pi[0] = 1;
```

| שם | אזור | מה שמור |
| --- | --- | --- |
| pi | מסגרת המחסנית של הקורא | הכתובת של ה-int הראשון |
| עשרת ה-int | ערימה | הערכים, לא מסוימים עד שכותבים |
| הוראות הפונקציה | אזור הקוד | קריאה בלבד |

כשהפונקציה חוזרת, התא בשם `pi` נעלם עם המסגרת. עשרת ה-`int` יושבים על הערימה. הם נשארים שם עד שמישהו מבצע `delete[]` על הכתובת הזו. אם הכתובת לא נשמרה במקום שממשיך לחיות, אין בתוכנית שם שאפשר לכתוב ב-`delete[]`. הבלוק נשאר מסומן כמוקצה. זו זליגת זיכרון של המערך, מאותו סוג ש-`leaky` מציירת.

:::problem id=worked-stack-array title="מצביע על המחסנית" source="Classes/Chapter 1 - The Memory Model.pptx" kind=worked solution_origin=source
אמרו איפה `ps` חי, איפה ה-`Student` חי, ומה נשאר אחרי ש-`main` חוזרת אם אף אחד לא קורא ל-`delete`.

```cpp
int main() {
    Student* ps = new Student("Avi");
    return 0;
}
```

:::solution
`ps` הוא מצביע מקומי, ולכן הוא תופס תא במסגרת המחסנית של `main`. אובייקט ה-`Student`, כולל תווי השם אם הבנאי (constructor) שם אותם בתוך האובייקט, הוא הבלוק ש-`new` החזיר, על הערימה.

```text
stack, main:  ps  ----------+
                             |
heap:                        v
                       Student("Avi")
```

כש-`main` חוזרת, המסגרת נשלפת והתא `ps` נעלם. בלוק הערימה לא משוחרר בשליפה הזו. בלי מצביע שנשאר אליו, יש זליגת זיכרון.
:::
:::

:::trap
`delete pi` אחרי `int* pi = new int[10]` משחרר ב-`delete` בלוק שהוקצה ב-`new[]`. צורת המערך היא `delete[] pi`. השחרור לא מתאים להקצאה, והרישום של הערימה נפגם: הסימון של מה שתפוס ומה שפנוי כבר לא מתאר את הבלוק. זו פגיעה בערימה. זליגת זיכרון היא מצב אחר: הכתובת אבדה, והבלוק עדיין מסומן כמוקצה.
:::

:::trap
משתנה גלובלי, וגם משתנה מקומי `static`, יושב באזור הסטטי לכל אורך הריצה. המסגרת לא מחזיקה אותו, ו-`new` לא הקצה אותו. `static` ברמת הפונקציה מאותחל פעם אחת.
:::

## תרגול

:::problem id=ps2-stack-vs-heap title="מחסנית מול ערימה" source="Exrecises/SPL_PS2 (1).pptx" kind=exercise solution_origin=source
לכל שורה, אמרו אם האחסון ששמו מופיע הוא על המחסנית או על הערימה, ואיזה `delete` נדרש.

```cpp
void demo() {
    int local = 2;
    int* one = new int(2);
    int* many = new int[10];
    string* s = new string("I'm on the heap");
}
```

:::hint
שם שמוצהר בתוך הפונקציה בלי `new` הוא מקומי. `new` ו-`new[]` הם הערימה.
:::
:::hint
התאימו את השחרור להקצאה: אובייקט אחד משתמש ב-`delete`, מערך משתמש ב-`delete[]`. משתנה מקומי על המחסנית לא נמחק ב-`delete`.
:::
:::hint
ב-`int local = 2;` אין `new`.
:::
:::solution
`local` הוא `int` במסגרת של `demo`. הוא משוחרר כש-`demo` חוזרת. אין `delete`.

`one` הוא מצביע במסגרת. ה-`int` שהוא מצביע אליו הוא אובייקט ערימה אחד, שמשוחרר ב-`delete one`.

`many` הוא מצביע במסגרת. עשרת ה-int הם מערך ערימה אחד, שמשוחרר ב-`delete[] many`.

`s` הוא מצביע במסגרת. אובייקט ה-`string` על הערימה, ומשוחרר ב-`delete s`. התווים שבתוך `std::string` הם הבעיה של האובייקט הזה. לא עושים להם `delete` בעצמכם.

אחרי שלושת ה-`delete` האלה המסגרת יכולה להיעלם בלי זליגת זיכרון. דילוג עליהם הוא זליגת זיכרון של בלוקי הערימה, לא של המצביעים.
:::
:::


:::examnote
שאלת הזיכרון נותנת מכולה קטנה ב-C++ ו-`main` שמעביר אותה לפי ערך אל `foo`, ומבקשת לצייר את המחסנית ואת הערימה בשורה מסומנת. המלכודת היא לצייר את החוצץ כאילו הוא חי במסגרת, או לצייר פרמטר לפי ערך כאילו הוא אותו אובייקט של הקורא.
:::

:::problem id=exam-15a-q2 title="וקטור כרשימה" source="Exams/15-a.pdf" kind=exam solution_origin=source
`vector` שומר איברים במערך רציף ויכול לשנות גודל. הקורס קובע שזה בזבזני, ומבקש `mvector<T>`, שהזיכרון שלו הוא בדיוק התאים שהוא צריך, שמורים כרשימה מקושרת.

א. ממשו את הפונקציות. מותר להוסיף עזרים. אסור להוסיף שדות או לשנות חתימות. `insertAt` תמיד מצליח, מקצה אם הוא חייב, ומכניס ב-`pos`. `removeAt` מקטין את המבנה, ואם `pos` ריק מחזיר איזשהו `T` דמה. גישה לתא ברשימה מקושרת אינה O(1).

ב. יוסי מציע למחוק את השדה `_len` ולהחזיר את `sizeof(_head)` כאורך. בחרו את התיאור הטוב ביותר.

1. זה עובד ומחזיר את האורך.
2. כמעט: צריך לחלק ב-`sizeof(T)`.
3. במכונה של 32 סיביות זה תמיד מחזיר 4.
4. זה לא עובר קומפילציה, כי אי אפשר להשתמש ב-`sizeof` עם תבנית (template).
5. אף אחת מהתשובות.

ג. ציירו את המחסנית, את הערימה, ואת ה-vtable בהערה המסומנת, עבור קריאה לפי ערך `foo(mvector<T> vec)`.

שלד המחלקה (class) בפתרון הרשמי הוא רשימת `node<T>` עם `_len` ו-`_head`, ועוד `getSize`, `pushAt` ו-`popAt`.

:::hint
`sizeof` הוא גודל של טיפוס בזמן קומפילציה, לא ספירה של צמתים שמגיעים אליהם בהליכה על `_next`.
:::
:::hint
פרמטר שמתקבל לפי ערך הוא אובייקט שני. איבר המצביע שלו ואיבר המצביע של הקורא הם שני תאים במחסנית. האם הם חולקים רשימה אחת תלוי בדיוק בבנאי ההעתקה (copy constructor).
:::
:::hint
ל-`_head` יש טיפוס של מצביע. במכונות של 32 סיביות שהשאלה הזו חושבת עליהן, מצביע הוא 4 בתים.
:::
:::solution
א. הפתרון הרשמי שומר `node<T>` מקושר חד-כיוונית ואורך. ההורס (destructor) הולך על `_len` צמתים ועושה `delete` לכל אחד. `copy` מקצה צומת חדש לכל איבר, ובנאי ההעתקה משתמש בה. ההשמה בפתרון הזה קוראת ל-`copy` ומחזירה `*this` (היא לא הורסת קודם את הרשימה הישנה; השמה שלמה צריכה גם לשחרר את הצמתים הקודמים, אחרת יש זליגת זיכרון). `pushAt` הולך עד `pos`, ממלא חוליות חסרות בצמתים ברירת מחדל, ואז מקשר צומת שמחזיק את `val`. `getSize` מחזיר את `_len`.

ב. הפתרון הרשמי מסמן את 3. `_head` הוא מצביע. `sizeof(_head)` הוא הגודל של המצביע הזה, שהוא 4 במכונה של 32 סיביות, לא מספר האיברים. חלוקה ב-`sizeof(T)` היא עדיין גודל של מצביע, לא אורך. הביטוי כן עובר קומפילציה בתוך תבנית.

ג. בשורה שבתוך `foo`, ה-`mvector` של הקורא הוא אובייקט אחד והפרמטר `vec` הוא אובייקט אחר, כי הפרמטר מועבר לפי ערך. כל אובייקט תופס תא במחסנית (המצביע `_head` ו-`_len`). הצמתים על הערימה. הערות הבדיקה מורידות על כתובת חזרה חסרה, על ציור של הפרמטר כאילו הוא לא הועבר לפי ערך, על הנחת אובייקט ה-vector עצמו על הערימה, ועל vtable שאין למחלקה. ציורים של העתקה רדודה (shallow copy) התקבלו: מצביעי `_head` של שני אובייקטי המחסנית יכולים לכוון אל שרשרת צמתים אחת אם בנאי ההעתקה לא היה העתקה עמוקה (deep copy). העתקה עמוקה מציירת שרשרת שנייה.
:::
:::

:::problem id=exam-15b-q2 title="וקטור שגדל" source="Exams/15-b.pdf" kind=exam solution_origin=source
`mvector` הוא עכשיו מערך של `node`, לא רשימה. `insertAt` ב-`pos` מעבר לסוף מגדיל את המערך לחזקה הקטנה ביותר של 2 שגדולה ממש מ-`pos` (וקטור ריק, הכנסה ב-5, נעשה באורך 8). `removeAt` מקטין בחצי אחרי שכל איבר בחצי העליון הוסר (אורך 8, אחרי שארבעת האיברים הגבוהים נעלמו, נעשה 4). האיברים שומרים על האינדקסים שלהם. ל-`node` יש `duplicate()` וירטואלית טהורה.

א. ממשו את הפעולות המסומנות, כולל בנאי העתקה עמוקה. מותר עזרים. אסור להוסיף שדות או לשנות חתימות.

ב. `my_node` יורש מ-`node` ומוסיף `long _data`. הניחו שהפונקציות שלו נכונות. ציירו מחסנית וערימה עבור הריצה הזו, עד ההערה:

```cpp
void foo(mvector vec) {
    mvector my_vec(vec);
    // ***** here *****
}
void main() {
    mvector vec;
    node* n = new my_node("test");
    vec.insertAt(*n, 3);
    foo(vec);
}
```

ג. מישהו מוסיף, בסוף `main`:

```cpp
my_node* m = (my_node*)(vec.getAt(0));
```

בחרו את המשפט הטוב ביותר.

1. המרה כלפי מטה (downcast) אסורה ב-C++, ולכן זו שגיאה.
2. המרה (cast) אף פעם לא יכולה לבדוק תאימות בזמן קומפילציה.
3. המרה כלפי מטה בטוחה רק כשלמחלקה אין מתודות וירטואליות.
4. מתודות וירטואליות נקשרות מאוחר, בזמן ריצה.
5. אף אחת מהתשובות.

:::hint
הגידול הוא "חזקת השתיים הקטנה ביותר שיכולה להכיל את האינדקס `pos`", והתאים הישנים מועתקים לפי ערך אל המערך החדש לפני שהמערך הישן נמחק.
:::
:::hint
`foo` מקבלת `mvector` לפי ערך, ואז בונה את `my_vec` בהעתקה מהפרמטר הזה. ספרו שלושה אובייקטי vector, לא אחד.
:::
:::hint
`getAt` מחזיר `node*`. השורה שנוספה היא המרה בסגנון C. האפשרויות הרשמיות עוסקות במה שנכון לגבי פונקציות וירטואליות, לא בשאלה אם ההמרה יפה.
:::
:::solution
א. בנאי ההעתקה הרשמי מקצה מערך חדש של `_len` ומציב בכל תא מהמקור. `insertAt`, כאשר `pos >= _len`, קובע את האורך החדש לחזקה הבאה של 2 מעל `pos`, מקצה, מעתיק את התאים הישנים, עושה `delete` למערך הישן, ואז כותב את האיבר החדש ב-`pos` ומסמן אותו כתפוס. `removeAt` מנקה את התא, וכאשר החצי הגבוה כולו פנוי, מקצה מערך באורך חצי, מעתיק, ומוחק את הישן. כי `node` פולימורפי, העתקה עמוקה באמת של תא `my_node` חייבת לעבור דרך `duplicate()` ולא לחתוך (slicing) את התא אל `node` רגיל. לולאת ההעתקה שפורסמה מציבה תאים. זה שלד הפתרון הרשמי, והוא יחתוך אם השמת `node` לא קוראת ל-`duplicate`.

ב. `n` מצביע אל `my_node` על הערימה. `vec` חי במסגרת של `main`. המערך שלו על הערימה, גדל ל-8, עם העותק של הצומת באינדקס 3. הקריאה `foo(vec)` בונה בהעתקה את הפרמטר `vec` במסגרת של `foo` (מערך שני על הערימה אם ההעתקה עמוקה). `my_vec(vec)` הוא vector שלישי במסגרת של `foo` ומערך שלישי. מצביע ה-vtable יושב בכל `my_node`, כי `duplicate` וירטואלית.

ג. הפתרון הרשמי מסמן את 4. מתודות וירטואליות נפתרות בזמן ריצה. משפט 1 שגוי: C++ מתירה המרה כלפי מטה. משפט 3 הופך את תנאי הבטיחות: `dynamic_cast` בדוק צריך לפחות מתודה וירטואלית אחת. השורה כפי שהיא כתובה היא המרה בסגנון C, והיא לא מבצעת את הבדיקה הזו.
